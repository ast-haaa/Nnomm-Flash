0. What is this Project About? (The Real-World Business Problem)

In Simple Terms:
Nnomm is a flash-deal food platform (similar to Swiggy Dineout, Zomato Gold, or Groupon). Restaurants publish limited-quantity, heavily-discounted offers (e.g. "50% off Luxury 5-Course Dinner — Only 10 vouchers available at 8:00 PM!").

This repository is the core, mission-critical reservation & claim backend engine designed to handle the intense traffic spikes when thousands of customers compete for those 10 units at the exact same millisecond.

1. Executive Architecture Overview

The Nnomm Flash-Deal Claim Service is engineered to solve the classic distributed systems challenge: high-concurrency flash sales with zero overselling, zero duplicate claims, sub-millisecond data consistency, and crash resilience across multiple horizontally-scaled instances.

Core Architectural Principles

  • Database as the Source of Truth: When multiple stateless service instances process claims concurrently, JVM-level synchronization (synchronized, ReentrantLock, Kotlin Mutex) is completely useless. Serialization is enforced at the database layer via PostgreSQL's tuple-level locks (SELECT ... FOR UPDATE) and storage-level check constraints.
  • Zero ORM Overhead: Rather than using heavy ORMs (like Hibernate/JPA or Exposed) that hide SQL queries, Nnomm uses raw parameterised JDBC prepared statements with HikariCP. Every SQL query is explicit, inspectable, and optimized.
  • Strict 2-Phase Idempotency: Every mutation requires an Idempotency-Key. The service registers an in-progress lock before touching stock, commits the result transactionally, and auto-recovers from node crashes via a 60-second lease timeout.
  • Non-Blocking Expiry Sweeping: Expired claims are reclaimed by a background coroutine worker utilizing PostgreSQL's FOR UPDATE SKIP LOCKED, allowing multiple worker nodes to run simultaneously without lock contention or deadlocks.
  • Constant-Time Security: Webhooks and JWT tokens are verified using timing-safe operations (MessageDigest.isEqual) to prevent side-channel timing attacks.

Recipe 5: Scaling to 100,000 Claims/Sec (Redis Pre-Allocation Architecture)

If an interviewer asks: "Postgres handles ~3,000 claims/sec on a single beefy instance. How do you scale this to 100,000/sec during a massive Black Friday event?"

  1. Redis Lua Scripting for Atomic Inventory Check & Decrement:
    • Load deal inventory into Redis: deal:{id}:stock = 1000.
    • Execute a single Redis Lua script that checks stock >= quantity, decrements atomically, and records customer claim in a Redis Set (for 1-claim limit). This executes in 0.2 milliseconds in single-threaded Redis memory.
  2. Asynchronous Kafka Event Queue:
    • Once Redis accepts the claim, push a ClaimReservedEvent to an Apache Kafka topic partitioned by deal_id.
    • A consumer service pool reads from Kafka and asynchronously inserts the claim into PostgreSQL in batches.
  3. Eventual Consistency with Strict Bounds: PostgreSQL is protected from traffic spikes, while Redis acts as the high-throughput throttle guarantee.

Network failures and client retries are handled through a durable 2-phase idempotency protocol stored in the idempotency_keys table:

5. Staff-Level Technical Interview Questions & Answers

These are 15 deep, realistic questions commonly asked at top tech companies (Uber, Amazon, Stripe, DoorDash, Swiggy) for Backend and Distributed Systems roles.

Q1: Why did you use PostgreSQL row-level locks (FOR UPDATE) instead of a Kotlin Mutex or Java synchronized block?

Answer: Mutexes and synchronization primitives only operate within the memory space of a single JVM process. In production, we run multiple service instances behind a load balancer (as demonstrated in our docker-compose.yml running Instance 1 on 8080 and Instance 2 on 8081). Two requests routed to different instances would acquire two separate local mutexes simultaneously, resulting in a race condition and overselling. PostgreSQL provides a single, centralized lock manager in shared memory that coordinates across all instances.

Q2: What is the purpose of SKIP LOCKED in the background expiry worker?

Answer: Without SKIP LOCKED, if we run multiple instances of the expiry worker, Worker 1 would issue SELECT ... FOR UPDATE and lock the first 50 rows. Worker 2 running the same query would block and stall waiting for Worker 1 to finish, causing latency and thread starvation. With SKIP LOCKED, PostgreSQL skips any row that is currently locked by another transaction, allowing Worker 2 to immediately pick up the next batch of rows without waiting or deadlocking.

Q3: How do you prevent webhook replay attacks?

Answer: We enforce three independent layers of defense:
1. Timestamp Check: The webhook header contains a Unix timestamp. We reject any request where |now - timestamp| > 300 seconds (5 minutes). This prevents attackers from replaying captured packets later.
2. HMAC Signature: The payload signature is computed over timestamp + "." + rawBody using HMAC-SHA256. An attacker cannot tamper with the timestamp without invalidating the signature.
3. Database Deduplication: We record every processed event_id in the payment_events table. If the same event_id arrives again, our unique constraint catches it and we return HTTP 200 without re-processing.

Q4: Why do you return HTTP 404 instead of HTTP 403 when a customer requests a claim belonging to someone else?

Answer: This is a crucial security practice known as preventing Resource Enumeration and Information Disclosure. If we returned 403 Forbidden, an attacker could iterate through UUIDs to discover which claim IDs exist on our platform. Returning 404 Not Found ensures that an unauthorized user cannot distinguish between a claim that does not exist and a claim belonging to another customer.

Q5: What happens if the server crashes after decrementing stock and creating the claim, but before returning the HTTP 201 response to the client?

Answer: The claim and the HTTP response status (201) are saved in the database within the same atomic transaction. When the client's network library inevitably times out and retries with the same Idempotency-Key, the service queries idempotency_keys, finds the completed record, and replays the stored 201 Created response with the header Idempotent-Replayed: true. No new claim is created, and no inventory is deducted twice.

Q6: What happens if the server crashes *during* the transaction before committing?

Answer: When the server process or container terminates, the TCP connection to PostgreSQL drops. PostgreSQL detects the socket disconnect and automatically issues a ROLLBACK on any open transaction. Stock is not decremented, and no claim is created. Furthermore, the idempotency_keys row has a locked_until lease of 60 seconds. During those 60 seconds, retries receive 409 Conflict (REQUEST_IN_PROGRESS). Once 60 seconds pass, the expired lock is renewed and the retry executes cleanly.

Q7: Why did you choose raw JDBC over an ORM like Hibernate or Exposed?

Answer: For high-concurrency systems, predictability of SQL execution is paramount:
1. ORMs frequently introduce N+1 query problems and automatic dirty-checking flushes that can hold database row locks longer than necessary.
2. Explicit constructs like FOR UPDATE SKIP LOCKED and database check constraints are first-class in raw SQL.
3. Performance: Raw JDBC prepared statements with HikariCP connection pooling have virtually zero CPU and memory allocation overhead compared to reflection-heavy ORM entity managers.

Q8: Why is MessageDigest.isEqual used in HMAC verification instead of standard string equality (==)?

Answer: Standard string equality operators (like strA == strB or .equals()) exit early on the first mismatched character. An attacker measuring request response times with high-precision network probes can determine how many leading bytes of their forged signature matched, allowing them to brute-force the signature byte-by-byte (a timing attack). MessageDigest.isEqual executes in constant time regardless of where the mismatch occurs, neutralizing timing attacks.

Q9: What database isolation level does the service use, and why is it sufficient?

Answer: We use PostgreSQL's default READ COMMITTED isolation level. While READ COMMITTED is vulnerable to non-repeatable reads in ordinary queries, we use explicit pessimistic locking (SELECT ... FOR UPDATE) on both the deal row and the claim row. In PostgreSQL, FOR UPDATE locks the row tuple directly, forcing concurrent transactions to serialize. This gives us strict serializability on mutating paths without paying the high abort-and-retry cost of SERIALIZABLE isolation level.

Q10: Why do we have database-level check constraints (CHECK (stock_available >= 0)) if the application code already checks stock?

Answer: Defense-in-depth. Application code can have bugs, developer oversights, or unexpected edge cases during schema refactoring. A database check constraint is an inviolable mathematical invariant enforced by the storage engine itself. If any query ever attempts to set stock_available below zero, PostgreSQL immediately aborts the transaction with an error, preventing catastrophic inventory overselling under any circumstance.

Q11: How do you handle lazy claim expiration on GET /v1/claims/{id}?

Answer: The background expiry worker runs on a 10-second interval. It is possible that a claim passes its expires_at timestamp 2 seconds before the worker's next tick. If the customer calls GET /v1/claims/{id} during this 2-second window, the brief requires that the API must never display it as RESERVED. In ClaimRoutes.kt, when reading the claim, if status == RESERVED && Instant.now().isAfter(expiresAt), the API dynamically maps the returned status in the JSON response to EXPIRED.

Q12: How would you prevent a distributed denial-of-service (DDoS) attack targeting the claim endpoint?

Answer:
1. Payload Limiter: We restrict incoming request bodies to 16KB max using our PayloadLimitPlugin.
2. Rate Limiting at Edge/API Gateway: Implement Token Bucket or Leaky Bucket algorithms (e.g. via Cloudflare or AWS API Gateway / Kong) based on IP address and Customer ID (e.g. max 5 requests per second per IP).
3. Fast-Path Cache Validation: In front of the database, check an in-memory Redis boolean flag deal:{id}:is_active. If the deal has already ended or is marked sold out, reject incoming requests immediately at the edge without querying PostgreSQL.

Q13: Why is the payment amount verified against deals.price_paise * quantity in the webhook?

Answer: Payment gateways can occasionally be misconfigured, or a malicious client might have altered the price on the frontend before calling the payment SDK. If the webhook reports a paid amount less than the required amount, we transition the claim status to NEEDS_REVIEW rather than granting the deal. This alerts human operations to audit the discrepancy while preventing inventory loss.

Q14: How does the system handle database connection pool exhaustion under load?

Answer: We use HikariCP configured with bounded parameters: maximumPoolSize = 20, connectionTimeout = 5000ms. If all connections are occupied, incoming requests wait up to 5 seconds before failing fast with a 503 Service Unavailable rather than hanging indefinitely. More importantly, our transactions are designed to do only pure SQL operations—no network calls, webhook dispatches, or heavy computations are ever made while holding an active database connection.

Q15: How were the tests written to guarantee concurrency correctness?

Answer: We use embedded real PostgreSQL with Kotlin Coroutines async(Dispatchers.IO). In ConcurrencyTest.kt, we fire 200 simultaneous coroutine workers claiming a 50-unit deal concurrently using awaitAll(). We verify that exactly 50 succeed, 150 receive 409 Sold Out, and the database stock_available ends at exactly 0. We also test 25 simultaneous requests with the exact same Idempotency-Key, confirming that exactly one claim is created.
